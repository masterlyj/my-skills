# 画面理解与抽帧：用法与依据

本文件说明 `scripts/vision.py` 的用法、抽帧策略的文献依据，以及为什么
不能按「场景分数」选帧。**改动抽帧相关逻辑前必须先读这一份。**

脚本需要 Pillow + numpy，且**运行前需先激活你自己的 Python 环境**
（安装方式见主 SKILL.md 步骤 0）。脚本不假定环境装在哪，也不自行创建环境。

下面的命令都**默认当前目录是 skill 目录**（`scripts/` 相对 SKILL.md 所在目录）。
工作目录不对时请先 `cd` 过去，详见主 SKILL.md 的「路径约定」。

---

## 一、三条命令

```powershell
# 1. 抽帧：从视频里选出适合读图的关键帧
python scripts/vision.py frames "<视频>" --outdir "<输出目录>" --count 30

# 2. 解读：逐张理解图片（文字 + 图示关系 + 要点）
python scripts/vision.py understand "<图片或目录>" --batch --output "<输出文件>"

# 3. 提问：就单张图做具体提问
python scripts/vision.py ask "<图片>" --question "这张架构图分了几层？"
```

- `understand` 是默认模式；`--raw` 才退化为纯文字转录
- `--batch` 用于目录，会在结果里标注每张图的来源
- 必须配置环境变量 `VISION_API_KEY` 和 `VISION_BASE_URL`，端点没有默认值。
  `VISION_BASE_URL` 填服务商提供的 OpenAI 兼容基础地址（包含所需的 `/v1` 等路径，
  不含 `/chat/completions`）；真实配置保存在本机环境中，文档仅使用占位符。

```powershell
$env:VISION_BASE_URL = "<服务商提供的基础地址>"
$env:VISION_API_KEY = "<你的 key>"
$env:VISION_MODEL = "<当前接口可用的视觉模型 ID>"
```

### 选择已有多模态模型

模型优先级为 **`--model` > `VISION_MODEL`**，两者都未配置时停止并提示；脚本无内置模型名。

1. 用户指定模型时使用该模型；否则读取本机 `VISION_MODEL`。
2. 尚未指定时，从当前 `VISION_BASE_URL` 对应服务的模型列表中选择。
   可查服务商控制台、文档，或其支持的 `/models` 接口，使用真实的模型 ID。
3. 确认候选模型支持通过 OpenAI 兼容的 `/chat/completions` 接口接收
   `image_url` 中的 base64 data URI，并返回文本。模型列表通常不提供完整能力信息，
   出现在列表里不代表支持视觉；以服务商能力说明或小规模单图验证为准。
4. 没有已确认可用的视觉模型时，询问用户或说明跳过画面理解，不猜模型 ID。

单次任务可以覆盖环境配置，批量解读中的所有图片使用同一选择：

```powershell
python scripts/vision.py understand "<图片或目录>" --batch --model "<视觉模型 ID>"
python scripts/vision.py ask "<图片>" --question "图中说明了什么？" --model "<视觉模型 ID>"
```

客户端自身可用的多模态模型不一定能通过此接口调用；只有当前端点与凭据可访问的模型
才能交给这个脚本。纯抽帧命令 `frames` 不需要模型或接口配置。

## 二、为什么默认「理解」而不是「OCR」

纯 OCR 只把图当扫描仪，丢掉了**版式、箭头、热力图分布**这些非文字但携带语义的信息。

**实测对比**（同一张 PPT 帧）：

| 模式 | 架构图帧得到的 | 热力图帧得到的 |
|------|---------------|---------------|
| 纯 OCR | 「3 层线性注意力 + 1 层全注意力，重复 16 次」 | 只有图表标题 |
| 理解模式 | 上述文字 + **箭头方向、模块角色分工、本页设计创新点** | 上述标题 + **颜色深浅代表重要性、专家分工规律、裁剪依据** |

理解模式输出四段：本页主题 / 完整内容 / 图示与关系 / 本页要点。

因此**只有明确只要文字时才用 `--raw`**。

## 三、抽帧策略：均匀采样 + 清晰度筛选

### 做法

1. 用 `ffprobe` 读时长 → 算出均匀间隔（`间隔 = 时长 / (2 × 目标帧数)`，下限 1 秒）
2. 按间隔均匀抽候选帧，候选约为目标帧数的 2 倍——**给清晰度筛选留余量**：
   `select_sharpest` 仅在候选多于目标时才评分，等量采样会让筛选形同虚设
3. 按**清晰度(权重 0.7) + 亮度(权重 0.3)** 的 z-score 加权评分，选出目标数量。
   候选不多于目标时（如短视频受 1 秒下限限制、抽不出 2 倍候选）原样返回；
   缺少 Pillow/numpy 时退化为均匀下采样
4. 重命名为连续编号替换旧的 `frame_*.jpg`；发布失败会尽力回滚旧帧，回滚失败时
   保留备份目录 `.frame-backup-*` 并在 stderr 给出路径；候选帧隔离在临时目录，
   不触碰输出目录里的其他文件

### 文献依据

| 来源 | 结论 |
|------|------|
| **arXiv:2509.14769**（首个控制变量的帧采样基准） | 长视频问答上，**均匀固定间隔采样全面优于各类自适应选帧**（MaxInfo、CSTA 等）；帧数越多越准，16→256 帧持续提升，256 帧后饱和 |
| **arXiv:2506.00667**（60 万小时生产实践） | 抽取候选帧后，用**清晰度 + 亮度**的 z-score 加权评分选帧，剔除模糊帧 |

### 为什么不能按「场景分数」选帧

早期版本用 ffmpeg 的 `scene` 分数排序取 Top-N，实测有两个致命问题：

1. **阈值不适配教程类视频**：实测某教程视频 10990 帧里，scene 分数
   P99 仅 0.033、最高 0.196。套用常见的 `0.3` 阈值会**一帧都抽不出来**。
2. **语义上根本错了**：scene 分数衡量「画面变化多大」，而高分帧往往是
   **过渡帧**——画面剧烈变化的那一瞬，伴随运动模糊或半透明叠加，**恰恰
   是最不适合读图的一帧**。文献也指出这类方法会
   "favor visually strong but semantically weak frames"。

一句话：读图需要的是「这帧清不清楚、信息完不完整」，与「画面变化多大」甚至负相关。

### 参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `--count` | 30 | 目标帧数。长视频要更高保真可到 60-100 |
| 采样间隔 | 自动 | 由时长算出，按目标数的 2 倍采样，下限 1 秒 |
| 清晰度权重 | 0.7 | 高于亮度，因为模糊对 OCR 的伤害更大 |
| 亮度权重 | 0.3 | 偏好较亮的画面；**不检测过曝**，纯白帧不因过曝被剔除 |

30 帧约 0.8 MB，是成本与覆盖的平衡点。

## 四、环境与依赖

- **ffmpeg / ffprobe 必须在 PATH 中**。新版 ffmpeg 已移除 `-vsync`，
  脚本用的是 `-vf fps=1/{interval}` 与 `-fps_mode`
- **清晰度筛选需要 Pillow + numpy**；缺失时脚本自动退化为纯均匀下采样，不报错
- **密钥绝不硬编码**：从 `VISION_API_KEY` 读取，缺失时报错并给指引
- **模型显式选择**：通过 `--model` 或 `VISION_MODEL` 指定，按上方规则确认视觉能力

### 已知限制

- 理解模式对**专有名词偶有识别偏差**（实测 `GSQ-RCQ`↔`GSQ-RCO`、
  `LynnStyle`↔`LymnStyle`），合并笔记时应与转录相互校验
- 理解模式做的是**图文语义解读**，对纯图形（无文字标注）也只能依据像素规律推断，
  不保证绝对准确
- 小红书等平台图片 URL 常需把 `http://` 换成 `https://` 才能下载
