# 项目 QA 整理

把**一个代码项目**的材料，整理成**能读懂、能讲出来、能记住**的 QA。用途是面试、答辩和考试。

## 先明确一件事：先讲懂，再谈记住

一份看不懂的材料，背下来也是废的——面试官追问一句就散了。所以这份材料的第一标准是**读者能读懂**，第二标准才是记住。

**读懂的门槛**：一个从没接触过这个项目的人，只读这一条 QA，不用翻源码、不用查资料，就能明白它是怎么回事。做不到就是没写清楚，不是读者水平不够。

由此推出三条贯穿全文的做法：

- **必须解释，不能只下结论。** 术语可以用，但首次出现要在当场用大白话讲明白它是什么。
- **正文写成能直接讲出来的话**，不写"详见某处"。
- **正文不放定位符号**（行号、文件路径）。它们是查阅用的，理解了也不增加一分；出处单独放证据层（见下）。

> 注意区分两类符号：**定位符号**（`app/service.py:1194`）不进正文；**概念术语**（幂等、最终一致性）该用就用——绕开术语去描写它，只会让句子变得拗口难懂。

## 适用范围

**用于**：为一个代码项目建立或维护 `qa/` 目录，把源码、配置、数据、设计文档里的事实改写成问答。

**不用于**：

- 只回答单个简单问题 —— 直接回答即可。
- 与代码项目无关的材料（理论学习、论文、流程制度）—— 五段式是为"问答本身就是材料原生形态"的场景设计的，套到论证链或条件表型材料上会强制一次有损转换。
- 评价候选人、打分或给录用建议。

## 与项目文档的分工

| | 项目文档（README / docs / repo-docs） | 本 Skill 产出的 `qa/` |
| --- | --- | --- |
| 回答什么 | "这个系统怎么工作" | "我能不能记住并讲清楚" |
| 组织方式 | 按模块和数据流 | 按**记忆地图**，同一层一个维度 |
| 成功标准 | 说明完整 | **合上材料能讲出来** |

不要照搬文档目录。同一个事实，文档里是机制说明，这里必须变成**读者从零也能读懂的一段话**。

## 铁律

1. **能读懂才算整理完。** 一个没接触过这个项目的人只读这条 QA 就能明白——做不到就回去重写，而不是把文档抄长。
2. **术语必须解释。** 领域术语可以用，但首次出现要当场用大白话讲清它是什么。**不解释的术语 = 没写。**
3. **正文零定位符号。** 行号、文件路径不进正文；术语名不受此限。出处单独放证据层。
4. **锚点要有区分度。** 见下方【关键词锚点】——雷同的锚点会主动削弱记忆。
5. **一个分类轴贯穿同一层。** 混用维度会让记忆地图失效。
6. **不编造事实。** 材料没写的不要补；说法冲突或没把握的，标 `[待确认]`。
7. **证据必须可追。** 每条结论都要能翻到出处，且出处会随代码漂移——所以必须按触发条件回来复核。

## 金字塔结构

三层，各司其职。**先背顶层，再用顶层定位下层。**

```text
qa/README.md              ← 顶层：定位 + 记忆地图 + 文件索引
   ├─ 域 1 ─────────────→  01-xxx.md   中观：域范围 + 五段式 Q&A + 证据索引
   ├─ 域 2 ─────────────→  02-xxx.md
   └─ 域 3 ─────────────→  03-xxx.md
```

| 层 | 在哪 | 承载什么 | 要求 |
| --- | --- | --- | --- |
| 顶层 | `README.md` | 一句话定位 + 域清单 + 文件索引 | 记住有哪几块 |
| 中观 | 每个域文件 | 域范围说明 + 域内 Q&A + 证据索引 | 记住这个域有哪些问题 |
| 微观 | 每条 Q&A | 五段式答案 | **先读懂，再记住核心答案** |

**为什么顶层要背**：层级结构本身的作用是充当**回忆时的检索计划**——先想起有哪几块，再从块里找具体答案。它不是一个需要额外背诵的目录，而是你回忆时的抓手。

这也决定了**顶层不要扇出过多**：一个挂着一二十个子项的顶层节点，本身就是一个弱线索（一个线索关联的项目越多，通过它回忆越难）。

### 顶层：`qa/README.md`

打开目录的第一眼就是它，所以它承担金字塔的顶点。**只放三样东西：定位、地图、文件索引。**

```markdown
# <项目名> QA

> <1–2 句：这个项目是什么，这份材料覆盖哪几块>

## 记忆地图

1. <域一> —— <一句话范围>
2. <域二> —— <一句话范围>
3. <域三> —— <一句话范围>

## 文件索引

| 文件 | 覆盖什么 | 什么时候翻 |
| --- | --- | --- |
| [01-xxx.md](01-xxx.md) | <域一范围> | <什么情况下翻它> |
| [02-xxx.md](02-xxx.md) | <域二范围> | <什么情况下翻它> |

## 复核记录

| 日期 | 触发原因 | 复核范围 | 结论 |
| --- | --- | --- | --- |

## 待确认

- [待确认] <缺什么>（影响：<哪条结论>）
```

要求：

- 地图**只到域这一层**，每个域一句话范围。**不要在这里逐条列出 Q 标题**——那会把地图淹掉，也会和域文件里的标题形成双份维护。
- 文件索引到**文件**这一层，说明每个文件覆盖什么、什么时候翻它。
- **不写任何答案正文。** README 变长就是在往这里抄内容，立刻拆回域文件。

### 中观：每个域一个文件

- 文件顶部写一句**域范围**，说明这个域收什么、不收什么。
- 接着按顺序写该域的 Q&A，每条一个 `###` 小节，**标题带 `Q` 编号**（`### Q1 ...`），五段式。编号在**本文件内**从 1 连续递增，是证据索引的引用依据。
- 文件末尾放**证据索引**（见下）。
- 域与文件**一一对应**，不要一个域跨两个文件，也不要一个文件塞两个域。

> 文件划分是**整理结构**，不是复习顺序。复习时按域交错、打乱顺序抽，不要从头到尾顺读——顺读时你会从上下文猜出答案，那种"答对了"不算数。

### 微观：每条问答的五个部分

顺序固定，不可增减、不可换位。

```markdown
### Q1 <简短问题标题>

【Q】<独立、明确的问题>

【讲清楚】
<主体段，不折叠。从零开始把这个概念讲到读者懂为止。
 见下方【讲清楚】的写法要求。>

【核心答案】
<1–3 句浓缩结论。如果面试只给 30 秒，你答的就是这一段。>

【关键词锚点】
关键词1 · 关键词2 · 关键词3 · 关键词4

<details>
<summary>【补充与边界】</summary>

- <数字、阈值、例外情况、易错点>
- <其他次要分支>

</details>
```

**五部分的顺序是刻意的：问题 → 讲清楚 → 核心答案 → 锚点 → 补充。**

- **【讲清楚】在最前且不折叠**：它是理解的主场。读者读到问题时脑子里是空的，必须先把这个概念立起来，后面的结论才有地方挂。
- **【核心答案】紧跟其后**：读懂了紧接着给一个浓缩版，用来背、用来在面试里开口。
- **【关键词锚点】放在结论之后**：它是**记忆工具**，不是理解工具。理解完了才需要它来做回忆钩子；放在最前面反而会在还没理解时干扰注意力。
- **【补充与边界】折叠**：这里放的是边角信息（数字、例外、次要分支），不懂也不影响理解主线。折叠让正文保持可扫读；**如果你发现某条补充其实对理解必不可少，它就不该待在这里，要挪进【讲清楚】。**

#### 【Q】问题

- 一个问题只问一件事；多个意图就拆成多条。
- 写成自然语言疑问句，接近真实的问法。
- **只合并纯措辞重复的问法**（"什么是幂等"和"幂等是什么意思"）。同一个事实的**不同入口各留一条**（定义向"什么是幂等"、因果向"为什么需要幂等"）——换个角度再问一遍几乎没有害处，反而多一个回忆入口。把别名收进关键词锚点即可。
- 要警惕的不是"重复"，而是**两条容易被互相混淆的近似问答**：它们会互相干扰。发现这种就合并或明确写出区别。

#### 【讲清楚】

**这是整份材料里最不能偷懒的一段。** 它的唯一职责是：让一个不懂的人读完就懂。

写法要求，逐条对照检查：

1. **从读者的空白状态起步。** 假设他完全不知道这个概念存在。先说他**能理解的处境或问题**，再说这个东西是怎么冒出来的。
2. **先用一句话说出它是干什么的**，再展开细节。不要一上来就讲机制。
3. **给一个具体的例子或类比。** 抽象描述讲不清的时候，一个贴切的比方顶十句定义。例子要具体到能想象出画面。
4. **句子主语必须是具体的东西。** "该系统实现了对外部依赖的解耦"——主语是"系统"，读者脑子里没有画面。换成"订单服务不再直接调用支付接口，而是把消息丢进队列就走"——能看见动作。
5. **禁止用未解释的抽象词。** 如果一个词本身就是你要解释的东西，可以留着；如果是**用来解释别人**的，那它必须先被解释。
6. **一步步推到结论，不要跳。** 中间的推理环节不能省——你觉得"显然"的那一步，读者往往恰好卡在那里。
7. **可以长。** 这一段不受篇幅限制，讲到懂为止。宁可长而清楚，不要短而含糊。

**自查办法**：把这一段单独拿给一个不懂这个项目的人看，问他哪里卡住了。或者自己换个身份读一遍：假如我没读过源码，这句话我能接住吗？

> 这一段和【核心答案】的区别：**【讲清楚】负责让人懂，【核心答案】负责让人背。** 前者可以啰嗦，后者必须精炼。两者不能互相替代——只有核心答案 = 记了一堆背不下来的结论；只有讲清楚 = 懂是懂了，面试时开口没重点。

#### 【核心答案】

浓缩结论，用来背、用来在面试里开口。

- 1–3 句，先给结论。
- 必须能脱离【讲清楚】独立成立——读完【讲清楚】的人，看到这段会觉得"对，就是这么回事"，而不是"这说的啥"。
- 不用循环定义，不用空泛口号，不只换一种说法复述问题。
- **保持短，但不要为了短而抽掉实质。** 把关键阈值、公式挪走之后，如果它变成了没有可检验内容的摘要，那它已经失去价值。

#### 【关键词锚点】

```text
幂等 · 结果缓存 · 分布式锁 · 重复处理
```

- 写**回忆线索**：术语、别名、英文名、缩写、相关概念，通常 3–6 个。
- **关键要求：锚点之间要有区分度。** 同一个线索关联的条目越多，通过它回忆越弱；如果十条问答都挂同一个大词（比如都写"幂等"），那个线索就废了。让每条的关键词指得出**这一条特有的是什么**。
- 用材料原本的语言，不要为了格式统一去音译或生造英文。
- 不用写 ID、编号或路径。
- 写完自测：**只看这一行，能不能把答案想起来**。想不起来就把缺的那个线索补上。
- 如果几条 Q&A 天然共享一个主题，可以在域范围说明里写清它们的关系和区别——把关系讲出来能缓解线索互相干扰。

#### 【补充与边界】

放在这里的是**边角信息**——不懂它也不影响理解主线。

- 数字、阈值、例外情况、易错点、次要分支。
- 保留关键条件和少而硬的数字，能记住的才写。
- 说法冲突时并列写出，标 `[待确认]`，不要静默拼成一个结论。
- **整段折进 `<details>`**，`<summary>` 写 `【补充与边界】`。

> **判断一段内容该放哪里**：能不能帮助读者**第一次读懂**？能 → 放【讲清楚】；不能，只是"知道更好" → 放这里。

## 两层材料：正文与证据

**正文零定位符号**（读懂和记忆时用），**证据单独一层**（被追问"你怎么知道的"时用）。

每个域文件末尾放该文件的证据索引，按 Q 编号列出出处：

```markdown
## 证据索引

- Q1 → `README.md:3`、`repo-docs/walkthroughs/one-real-run.md:3-7`
- Q2 → `app/service.py:1194-1238`、`clients/email_forwarder.py:36-54`
```

- 只写 Q 编号，**不重复 Q 标题**（标题在正文里已经有了）。
- Q 编号与正文 `### Q<n>` 标题**一一对应**，按文件内出现顺序。插入或删除条目时要重编后续编号，保持连续。
- 一个 Q 对多个出处时全部列出。

## 自测：两个阶段，别混着做

**先确认读懂了，再谈记住了。** 这两件事的检验方式完全不同：

### 阶段一：读懂了吗

- **做法**：拿一条 QA，只看【Q】，然后读【讲清楚】。读完问自己：**我能不能用自己的话把这件事讲给一个不懂的人听？**
- **卡住就说明没写清楚**——回去改【讲清楚】，不是硬读过去。
- **这个阶段不限时间、不看关键词锚点**。锚点是记忆工具，在这里只会干扰。
- **别跳过这一步。** 【核心答案】写得很顺、读着很对，不代表你懂了——它可能只是措辞流畅。

### 阶段二：记住了吗

**闭卷、隔天、口述。** 这三条缺一不可：

| 要求 | 为什么 |
| --- | --- |
| **闭卷** | 材料在眼前时的熟悉感会让人高估自己，那种"我都会"在考场上会碎掉 |
| **隔天** | 刚整理完就自测，测的是短期流畅，不是长期记住 |
| **口述** | 出声或写出来，才暴露"以为自己懂但讲不出"的地方 |

做法：合上全部文件，只看 README 的地图，逐个域自问"这里有哪些问题"，再对每条尝试讲出核心答案。讲不顺的先回去重读【讲清楚】——**不要靠重读自己的笔记来解决**。

顺带一个好消息：**讲错不算白费**。带着正确答案的检索（哪怕是失败的检索）比不检索记得更牢；而这份 QA 本身自带答案，正好提供了反馈。所以放心大胆地先答再看。

> **两个阶段的顺序不能反。** 没读懂就背，背下来的是噪音——面试官追问一句就散架了。

## 复核：证据会腐坏，必须回来查

证据层引用的是**会变的代码**。不写复核规则，它一两个月就烂掉，比不写更危险。

**触发条件**（满足任一即复核）：

- 被引用的代码、配置或数据发生改动。
- 上线状态变化（某个功能从"默认关闭"变成"灰度中"或反之）。
- 数字类结论过期（统计窗口滚动、样本量变化）。
- 每轮面试/答辩/考试前。
- 距上次复核超过 3 个月。

**怎么复核**：

1. 按证据索引逐个打开出处，确认结论仍然成立。
2. 数字重新对一次口径（窗口、分母、样本量），不要沿用旧值。
3. 发现结论已变：改正文与证据；**改变结论的旧值不要静默替换**，在复核记录里留一行。
4. 发现出处已消失（文件被删、函数被改名）：标 `[待确认]`，不要凭记忆改写。
5. 在 README 的**复核记录**表里登记：日期、触发原因、复核范围、结论。

## 工作流

思考是自下而上的，写作是自上而下的。**先读透材料，再定地图，最后填内容。**

### 新建

1. **读材料，别急着分类。** 读入口文件、配置、数据、已有文档。目标只有一个：**能用自己的话说出这个项目在干什么**。说不出来就继续读——这一步偷懒，后面全是抄文档。
2. **列问题清单**（内部完成，不写入输出）：提取显式与隐含问题；把藏了多个意图的问法拆开；只合并纯措辞重复的；剔除只在细节层面成立、不值得记忆的；留下**真正会被问到、且值得记住**的。
3. **定地图，先写 README。** 按下面的规则定域、写范围、把问题归位。地图没定就写域文件，必然返工。
4. **逐条写五部分。先写【讲清楚】，再压缩出【核心答案】。** 顺序不能反——先写核心答案容易变成背结论，而【讲清楚】里的推理环节会被省略掉，读者就再也读不懂了。【讲清楚】写完对照那 7 条写法要求自查一遍。
5. **回填证据索引**，逐个核对出处真实存在。
6. **按两阶段自测**（先读懂、再记忆）。

### 更新已有 `qa/`

1. **定位归属域。** 新内容先归到已有的域；确实放不进再考虑新增域——新增域要同步改 README 地图与文件索引。
2. **判断动作**：
   - 已有 Q 覆盖了这个问法（纯措辞重复）→ 只补关键词线索。
   - 是新的独立问题，或同一事实的**另一个入口** → 在所属域内追加，并补它的证据索引。
   - 材料变了导致答案过时 → 改【讲清楚】与【核心答案】，**命中下面复核的触发条件**。
   - 内容已失效 → 删除该条，并清掉它的证据索引行，重编后续 Q 编号。
3. **保持原有顺序与域划分**，只增补内容。重排会破坏肌肉记忆。
4. **主动标出缺口**：更新时发现的冲突或缺失，写进 README 的"待确认"，不要静默补一个看似合理的答案。

## 分类轴怎么选

顶层分类不是文件柜，是**脑子里那张地图**。先定轴，再填内容。

**同一个层只用一个维度。** 代码项目默认按**问题性质**切：

| 域 | 收什么 |
| --- | --- |
| 主链路 / 架构 | 项目做什么、请求怎么走、为什么这么设计 |
| 技术核心 | 项目里最有技术含量的那一块（模型、并发、算法、存储） |
| 业务规则 | 领域概念、边界条件、容易答错的细节 |
| 运维与风险 | 可观测性、上线与回滚、事故复盘、遗留问题、协作边界 |

要求：

- **顶层 3–5 个域**。多到记不住就说明切得太细。
- **每个域 5–10 条 Q**。明显超出就按同一轴再拆一层或拆域；只有两三条就并进相邻域。
- 归不进任何域 → 检查是轴选错了，还是这条不该收。
- 无法可靠归类 → 单独放"其他"，不要硬塞。

### 自测

遮住内容，只看 README 的地图，逐条问自己："这个域里有哪些问题？" 答不上来就调整分类，而不是硬背。

## 文件组织

```text
qa/
  README.md         顶层：定位 + 记忆地图 + 文件索引 + 复核记录
  01-<域>.md        域文件：域范围 + 五段式 Q&A + 证据索引
  02-<域>.md
  03-<域>.md
```

- 编号可选但推荐：它固定了整理顺序，也让新增域时有位置可插。
- 域文件名包含域名本身，不要只叫 `01.md`。
- 允许按需增加专项文件（数字速查、术语表、简历素材），条件是：在 README 文件索引里登记，且不重复五段正文。

## 质量检查

**可机械核对的：**

- [ ] README 里没有 Q 标题，只有域列表和文件索引。
- [ ] README 里没有任何答案正文。
- [ ] 顶层 3–5 个域，每个域大致 5–10 条 Q，域与文件一一对应。
- [ ] 每个域文件末尾有证据索引，Q 编号与正文 `### Q<n>` 标题一一对应，没有多余或缺失。
- [ ] 每条 Q&A 都按【Q】→【讲清楚】→【核心答案】→【关键词锚点】→（折叠的）【补充与边界】排列。
- [ ] 只有【补充与边界】折进了 `<details>`，其余四部分都没折。
- [ ] 正文里没有行号、文件路径。
- [ ] **每个术语首次出现时都当场解释了。**（逐个搜一遍术语，确认没有"裸用"）
- [ ] 【讲清楚】里没有出现未解释的抽象词。
- [ ] 【讲清楚】里有至少一个具体的例子或类比。
- [ ] **同一条结论里的数字在全文出现多次时完全一致。**
- [ ] 不确定的结论标了 `[待确认]`。
- [ ] README 的文件索引与实际文件一致，没有死链。

**需要自己判断的：**

- [ ] **把一条【讲清楚】单独拿给不懂这个项目的人看，他能读懂。**（最关键的一条）
- [ ] 【讲清楚】的句子主语是具体的东西，不是"该系统""该模块"这类空转的主语。
- [ ] 【核心答案】在读完【讲清楚】之后看，是"对，就是这么回事"，而不是"这说的啥"。
- [ ] 【核心答案】能脱离【讲清楚】独立成立。
- [ ] 只看关键词锚点能把答案想起来，且不同条目的锚点**互相区分得开**。
- [ ] 同一层只有一个分类维度，没有混用。
- [ ] 没有为了凑长度而写的段落。
- [ ] 复核记录里最近一次复核仍在有效期内。
