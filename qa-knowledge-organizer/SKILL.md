# 项目 QA 记忆整理

把**一个具体项目**的材料，整理成**能被记住、能被复述**的 QA。

输入是项目材料（源码、配置、数据、文档、设计说明）；输出是一套结构化问答。整理的终点不是"写全"，而是**合上材料后还能讲出来**。

## 与项目文档的分工

| | 项目文档（README / docs） | 本 Skill 产出的 QA |
| --- | --- | --- |
| 回答什么 | "这个系统怎么工作" | "我能不能记住并讲清楚" |
| 组织方式 | 按系统模块和数据流 | 按**记忆地图**，同一层一个维度 |
| 成功标准 | 说明完整 | **能被复述**，关键词能唤起答案 |

不要照搬文档目录。同一个事实，文档里是机制说明，这里必须变成"能背下来的一段话"。

## 铁律

1. **能背下来才算整理完。** 写不出 1–3 句核心答案，就说明还没真正理解——回去把材料读懂，而不是把文档抄长。
2. **正文里不放代码索引。** 变量名、行号、key 名会打断记忆。准备阶段可以查源码核对，但交付物里不出现。
3. **不编造事实。** 材料没写的不要补；说法冲突或没把握的，标 `[待确认]`。
4. **一个分类轴贯穿同一层。** 混用维度会让记忆地图失效。
5. **关键词锚点是回忆入口**，不是装饰。写完自测：只看锚点能不能把答案想起来。

## 记忆地图：分类就是第一层要背的东西

顶层分类不是文件柜，是**你自己脑子里的那张地图**。先记住地图，再用地图定位每一条答案。

要求：

- **顶层 3–5 个域**，多到记不住就说明切得太细。
- **同一层只用一个维度**。默认按"问题性质"切：主流程 / 技术核心 / 业务规则 / 运维与风险。
- 不要按难度、按代码模块、按文件夹切——这些不是人回忆问题的路径。
- 每个域下面**先记住域名和一句话范围**，再记域内的 Q。
- 每个域控制在 **5–9 条 Q**。超了就拆域；只有两三条就合并。

分类完成后应当能用一句话报出整张地图，例如：

```text
这个项目我分四块讲：它做什么和主链路、技术上的核心设计、
业务规则里的坑、以及运维和风险。
```

### 自测

遮住内容，只看分类树，逐条问自己："这个域里有哪些问题？" 答不上来就调整分类，而不是硬背。

## 每条问答的四段结构

顺序固定，不可增减、不可换位。

```markdown
### <简短问题标题>

【Q】<独立、明确、可搜索的问题>

【核心答案】
<1–3 句费曼式答案。合上材料也能独立复述。>

【展开说明】
- <原理或依据>
- <做法或过程>
- <示例、边界、例外>

【关键词锚点】
`<域>/<概念>` · 关键词1 · 关键词2 · 关键词3
```

### 【Q】问题

- 一个问题只问一件事；多个意图就拆成多条。
- 写成自然语言疑问句，接近真实被问到的说法。
- 相似问法合并成一条，把别名收进关键词锚点。

### 【核心答案】

这是**最需要打磨**的一段。

- 1–3 句，先给结论。
- 费曼式：假设听的人不懂术语，用最朴素的话讲清"是什么、为什么、怎么做"。
- 必须能脱离展开说明独立成立。写完遮住展开自测一遍。
- 不用循环定义，不用空泛口号，不只换一种说法复述问题。
- 无法简化的术语，首次出现时用半句话解释。

### 【展开说明】

- 只展开理解核心答案所必需的内容。
- 优先按"原理 → 做法 → 示例 → 边界"分点；没有对应内容就省略。
- 分点是为了好记，不是为了写长。**一份 QA 的价值密度在核心答案，不在展开**。
- 保留关键条件、因果关系、数字；但数字要少而硬，能记住的才写。
- 说法冲突时并列写出，标 `[待确认]`，不要静默拼成一个结论。

### 【关键词锚点】

```text
`<域>/<概念>` · 关键词1 · 关键词2 · 关键词3
```

- 第一个反引号字段是**稳定 ID**，用于定位和去重，全文唯一。
- ID 用小写英文、数字和连字符，域与概念之间用 `/`，例如 `pipeline/idempotency`。
- 概念含义没变就复用原 ID；不要因为改了标题就换 ID。
- 后续关键词写**回忆线索**：别名、英文名、缩写、相关概念。通常 3–6 个。
- 锚点是给未来的自己用的：看到它应当能想起这条答案。

## 输出格式

```markdown
# <项目名> QA

> <2–3 句：这个项目是什么，这份材料覆盖哪几块>

**记忆地图**

1. <域一> —— <一句话范围>
2. <域二> —— <一句话范围>
3. <域三> —— <一句话范围>

## 1. <域一>

<一句话说明这个域覆盖什么>

### <问题标题>

【Q】...

【核心答案】
...

【展开说明】
- ...

【关键词锚点】
`domain/concept` · ...
```

一份材料可以是一个文件，也可以按域拆多个文件。**拆文件时保持域与文件一一对应**，不要让一个域跨两个文件。

材料存在缺口时，在末尾追加：

```markdown
## 待确认

- [待确认] <缺什么>（影响：<哪条结论>）
```

## 工作流

### 1. 先读，别急着分类

读 `README`、入口代码、配置、数据文件、已有文档。目标只有一个：**能用自己的话说出这个项目在干什么**。

说不出来就继续读。这一步偷懒，后面全是抄文档。

### 2. 列问题清单

在内部完成，不写入输出：

1. 从材料里提取显式问题和隐含问题。
2. 一个问题的问法里藏了多个意图就拆开。
3. 合并语义等价的问题。
4. 剔除只在细节层面成立、不值得记忆的问题。
5. 留下**真正会被问到、且值得记住**的。

### 3. 搭记忆地图

按上文的分类规则定 3–5 个域，给每域写一句话范围，把问题归入。

- 归不进任何域 → 检查是分类错了，还是这条不该收。
- 无法可靠归类 → 单独放"其他"，不要硬塞。
- 域内超过 9 条 → 拆。
- 只有两三条 → 并。

分类定稿后，先写出那句能一口气报完的总结，再往下写。

### 4. 逐条写四段

先写核心答案，再补展开。顺序不能反——先写展开很容易变成抄文档。

核心答案写不顺，说明这条还没理解透，回去查材料。

### 5. 自测并交付

见下方质量检查。

## 质量检查

交付前逐项确认：

- [ ] 遮住分类内容，只看记忆地图，能说出每个域有哪些问题。
- [ ] 顶层 3–5 个域，每个域内 5–9 条 Q。
- [ ] 同一层只有一个分类维度，没有混用。
- [ ] 每条 Q 只有一个主要意图；重复问法已合并。
- [ ] 每条都按【Q】→【核心答案】→【展开说明】→【关键词锚点】排列。
- [ ] 每条核心答案遮住展开后仍能独立复述，且不超过 3 句。
- [ ] 正文里没有变量名、行号、key 名等代码符号。
- [ ] 数字少而硬，且都能说清来历；不确定的标了 `[待确认]`。
- [ ] 每个稳定 ID 全文唯一、格式一致，能代表该条的核心概念。
- [ ] 只看关键词锚点，能把对应的答案想起来。
- [ ] 展开说明里没有为了凑长度而写的段落。
